  <action>
    1. Add analyzer packages to CrowdQR.Api.csproj:
       - `AsyncFixer` (latest stable) - Roslyn analyzer for async anti-patterns
       - `Microsoft.VisualStudio.Threading.Analyzers` (latest stable) - Threading/async analysis
       Both should use PrivateAssets="all" since they're analyzers, not runtime dependencies.

    2. In Program.cs, change `AddDbContext` to `AddDbContextPool`:
       - Replace `builder.Services.AddDbContext<CrowdQRContext>(options => ...)` with `builder.Services.AddDbContextPool<CrowdQRContext>(options => ...)`
       - This enables context instance reuse (2x faster, 10x less allocation per Microsoft benchmarks)
       - DbContext pooling requires that CrowdQRContext has no private state stored between uses. The current CrowdQRContext is stateless (only DbSets), so this is safe.

    3. Configure Npgsql connection pool sizing in the connection string:
       - Add `Maximum Pool Size=50;Minimum Pool Size=5;Connection Idle Lifetime=300;Connection Pruning Interval=10` to the connection string built in BuildConnectionString()
       - Also add these parameters to the GetConnectionString("Default") fallback path by appending them if not already present
       - 50 max connections is appropriate for a single-server app serving hundreds of concurrent users
       - 5 min connections keeps a warm pool ready

    4. Build the solution to verify analyzers don't flag any existing code as errors (since TreatWarningsAsErrors is true in Directory.Build.props). If analyzer warnings appear, fix them - they represent real async anti-patterns.

    Run: `dotnet build src/CrowdQR.API/CrowdQR.Api.csproj` to verify clean build.
  </action>

    - grep for "AddDbContextPool" in Program.cs confirms pooling enabled
    - grep for "Maximum Pool Size" in Program.cs confirms connection pool configured

       ```json

           "LogLevel": {
             "Default": "Information",
             "Microsoft.AspNetCore": "Warning",
             "Microsoft.EntityFrameworkCore.Database.Command": "Information",
             "Microsoft.EntityFrameworkCore.Query": "Warning"
           }
         }
       }
       ```
       - `Database.Command` at Information level logs SQL queries with parameters
       - `Query` at Warning level logs only query compilation warnings (not every query plan)
       - This follows the CONTEXT.md decision: "Use appsettings.Development.json to control profiling"

    2. In Program.cs, add development-only sensitive data logging to the DbContext pool configuration:
       ```csharp
       builder.Services.AddDbContextPool<CrowdQRContext>(options =>
       {
           options.UseNpgsql(connectionString);
           if (builder.Environment.IsDevelopment())
           {
               options.EnableSensitiveDataLogging();
               options.EnableDetailedErrors();
           }
       });
       ```
       - EnableSensitiveDataLogging shows parameter values in query logs (dev only for security)
       - EnableDetailedErrors provides better error messages in development

    3. Verify the application starts and query logs appear:
       Run: `dotnet build src/CrowdQR.API/CrowdQR.Api.csproj` to verify compilation.

    Note: Do NOT add `options.LogTo(Console.WriteLine)` - the built-in ILogger integration via appsettings is the standard approach and avoids duplicate logging.
