  <action>
    **Step 0: Async audit (bottom-up verification per CONTEXT.md)**
    Audit the codebase bottom-up to verify async correctness before proceeding:
    1. Data layer: Search all files in `Data/`, `Repositories/`, and `Services/` for sync-over-async anti-patterns: `.Result`, `.Wait()`, `.GetAwaiter().GetResult()`, synchronous `SaveChanges()` (should be `SaveChangesAsync()`), synchronous `ToList()` on queries (should be `ToListAsync()`), synchronous `FirstOrDefault()` (should be `FirstOrDefaultAsync()`).
    2. Services: Search all files in `Services/` for the same patterns. Verify all service methods that call the data layer use `await` properly.
    3. Controllers: Search all controller files for sync-over-async patterns.
    4. Fix any violations found. If all code is already async, document that finding in the summary.
    This audit implements the CONTEXT.md locked decision: "Bottom-up approach: Convert data layer to async first, then work up through services to controllers."

    **Step 1: Add project-level ConfigureAwaitOptions to Directory.Build.props**
    Per CONTEXT.md locked decision: "Use project-level setting (.csproj ConfigureAwaitOptions) rather than explicit calls everywhere."
    Add to the `<PropertyGroup>` in `Directory.Build.props`:
    ```xml
    <ConfigureAwaitOptions>SuppressDefault</ConfigureAwaitOptions>
    ```
    This eliminates the need for `.ConfigureAwait(false)` on every await call across the entire solution.

    **Step 2: Add analyzer packages to CrowdQR.Api.csproj:**
    - `AsyncFixer` (latest stable) - Roslyn analyzer for async anti-patterns
    - `Microsoft.VisualStudio.Threading.Analyzers` (latest stable) - Threading/async analysis
    Both should use PrivateAssets="all" since they're analyzers, not runtime dependencies.

    **Step 3: In Program.cs, change `AddDbContext` to `AddDbContextPool` with lazy loading disabled:**
    - Replace `builder.Services.AddDbContext<CrowdQRContext>(options => ...)` with `builder.Services.AddDbContextPool<CrowdQRContext>(options => ...)`
    - Add `options.UseLazyLoadingProxies(false)` OR explicitly call `options.UseQueryTrackingBehavior(QueryTrackingBehavior.TrackAll)` without enabling lazy loading proxies.
    - The correct way to disable lazy loading: ensure NO call to `UseLazyLoadingProxies()` exists AND add this line in DbContext configuration:
      ```csharp
      options.UseNpgsql(connectionString);
      // Explicitly disable lazy loading to prevent accidental N+1 patterns (CONTEXT.md locked decision)
      options.UseLazyLoadingProxies(false);
      ```
      NOTE: If `Microsoft.EntityFrameworkCore.Proxies` package is not referenced, lazy loading via proxies is already impossible. In that case, also disable the without-proxies lazy loading in CrowdQRContext.cs constructor:
      ```csharp
      protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
      {
          // Do NOT add: optionsBuilder.UseLazyLoadingProxies();
      }
      ```
      AND in the DbContextPool options:
      ```csharp
      options.ConfigureWarnings(w => w.Throw(CoreEventId.LazyLoadOnDisposedContextWarning));
      ```
    - DbContext pooling requires that CrowdQRContext has no private state stored between uses. The current CrowdQRContext is stateless (only DbSets), so this is safe.

    **Step 4: Configure Npgsql connection pool sizing in the connection string:**
    - Add `Maximum Pool Size=50;Minimum Pool Size=5;Connection Idle Lifetime=300;Connection Pruning Interval=10` to the connection string built in BuildConnectionString()
    - Also add these parameters to the GetConnectionString("Default") fallback path by appending them if not already present
    - 50 max connections is appropriate for a single-server app serving hundreds of concurrent users
    - 5 min connections keeps a warm pool ready

    **Step 5: Build the solution to verify analyzers don't flag any existing code as errors** (since TreatWarningsAsErrors is true in Directory.Build.props). If analyzer warnings appear, fix them - they represent real async anti-patterns.

    Run: `dotnet build src/CrowdQR.API/CrowdQR.Api.csproj` to verify clean build.

    1. Create or update `src/CrowdQR.API/appsettings.Development.json` with EF Core query logging AND Npgsql connection pool event logging:
       ```json
       {
         "Logging": {
           "LogLevel": {
             "Default": "Information",
             "Microsoft.AspNetCore": "Warning",
             "Microsoft.EntityFrameworkCore.Database.Command": "Information",
             "Microsoft.EntityFrameworkCore.Query": "Warning",
             "Npgsql.ConnectionPool": "Information",
             "Npgsql": "Warning"
           }
         }
       }
       ```
       - `Database.Command` at Information level logs SQL queries with parameters
       - `Query` at Warning level logs only query compilation warnings (not every query plan)
       - `Npgsql.ConnectionPool` at Information level logs connection pool open/close/idle events (CONN-02 monitoring)
       - `Npgsql` at Warning level logs general Npgsql warnings without flooding
       - This follows the CONTEXT.md decision: "Use appsettings.Development.json to control profiling"
       - This satisfies CONN-02 "Connection pool metrics monitored" for the development environment

    2. In Program.cs, add development-only sensitive data logging to the DbContext pool configuration:
       ```csharp
       builder.Services.AddDbContextPool<CrowdQRContext>(options =>
       {
           options.UseNpgsql(connectionString);
           if (builder.Environment.IsDevelopment())
           {
               options.EnableSensitiveDataLogging();
               options.EnableDetailedErrors();
           }
       });
       ```
       - EnableSensitiveDataLogging shows parameter values in query logs (dev only for security)
       - EnableDetailedErrors provides better error messages in development

    3. Enable Npgsql connection pool statistics logging. In Program.cs, add after the DbContextPool registration (dev only):
       ```csharp
       if (builder.Environment.IsDevelopment())

       }
       ```
       Alternatively, Npgsql 8+ auto-integrates with ILoggerFactory when registered via `UseNpgsql()`, so the appsettings-based logging may be sufficient. Verify by checking if connection pool events appear in console output during startup. If not, add the explicit initialization above.
